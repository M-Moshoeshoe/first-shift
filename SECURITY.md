# Security and the secure development lifecycle (SSDLC)

First Shift handles young people's identity details, phone numbers, business locations and payment confirmations. This document records how we thought about security at every stage of building it, and how we check that the controls work. It is the basis of our SSDLC submission for the FNB App of the Year Hackathon 2026.

## What we protect

| Asset | Why it matters |
| --- | --- |
| Young people's ID data, photos and phone numbers | Identity theft and harassment |
| Business locations | A young person's safety depends on them being real |
| References and payment records | The whole product rests on these being honest |
| Fees due | Our revenue record |
| API keys and the ID hashing secret | Abuse and cost |

The worst outcome isn't a data leak. It's a fake tryout that puts a young person in danger, so safety rules sit inside the security design.

## Our lifecycle

1. **Design:** every feature starts from `docs/RULES.md`, with its risks listed in this file before it's built.
2. **Build:** rules live in pure, tested domain functions; security-relevant decisions are never made in prompts or UI code (`AGENTS.md`).
3. **Review:** each phase ends with a diff review against `AGENTS.md` before it's accepted.
4. **Test:** unit tests, security rules tests, build-time checks and scans, below.
5. **Deploy:** secrets only in Netlify environment variables; `/api/health` confirms configuration without exposing values.
6. **Monitor and respond:** structured logs for rejected writes and AI failures, and a disclosure contact below.

## Threats and controls (OWASP Top 10:2025)

| Risk | How it could hit us | Control | How we test it |
| --- | --- | --- | --- |
| A01 Broken Access Control | A user reads someone else's booking or edits a tryout they don't own, reads ID hashes or the audit log, or skips onboarding to reach another role's screens | Firestore and Storage rules deny by default; every write goes through a server route that verifies the Firebase ID token and ownership; account screens sit behind ProfileGate, which opens each one only while it's the person's destination (`redirectFor`), and the server routes enforce every rule again regardless | `tests/rules`: no client reads `idHashes` or `auditLog`, no client writes `users` or `businesses`, each person reads only their own user record; photos only into your own folder, images only, under 2 MB. Loosening a rule on purpose makes these tests fail. `tests/unit/routing.test.ts` covers every screen against every profile state. Tryouts: no client can create, change or delete one, and one waiting for review is readable only by its owner (`tests/rules`); withdrawing someone else's tryout reads as not found, so ids can't be probed (`tests/unit/tryoutService.test.ts`). Only a tryout's owner reads it directly; young people get the feed and each tryout from the server, never its exact pin. Applications: readable only by the applicant and the tryout's owner, written only by the server, one per young person per tryout (the id is built from both), each with its audit entry and the tryout's applicant count in one transaction (`tests/rules`, `tests/unit/findingService.test.ts`). A tryout from the other world (demo or real) reads as not found on every route (`npm run e2e:demo`). Bookings: readable only by their two parties; the check-in code and the share token live in `bookingSecrets`, which no client can read, so the owner can't see the code they must be shown at the door; review cases and strikes are server-only. Photos: Storage lets each person read only their own folder; anyone else's photo comes through `GET /api/photos`, which checks the two are linked by an application or a booking (`mayViewPhoto`), so a demo account can't read a real person's photo even with its path. The public status page is served by the server for an unguessable 144-bit token and shows first names, the business, the times and the status only, until midnight after the tryout; an unknown and an expired token look the same. ESLint stops pages and components importing server code. The day: only the owner can check in, with all three door checks and the code; wrong codes are counted and lock the booking after 5, so an owner can't guess a young person into "present"; the last four ID digits reach the owner only for the door check, only while the booking waits for it (`tests/unit/day.test.ts`, `dayService.test.ts`). Proof in a dispute: a screenshot is accepted only after Not received, once from each side; it's sent to the server, which reads the file's own first bytes (JPEG, PNG or WebP only, under 2 MB) and stores it at a path it builds itself, `evidence/{booking}/{side}-{random}`, so nothing is overwritten; no client can read or write the `evidence` records or the `evidence/` files, not even the person who sent one, so only an admin sees them (`tests/rules`, `tests/unit/evidence.test.ts`, `npm run e2e:demo`) |
| A02 Security Misconfiguration | Open rules, verbose errors, missing headers, a test switch left on in production | Security headers in `next.config.ts` (CSP, HSTS, frame-ancestors, Referrer-Policy, Permissions-Policy); errors return safe messages only; the emulator switch connects the browser only when it is `"true"` and the page is on `localhost`, and `/api/health` reports it; the test-only emulator sign-in needs a development build AND the switch AND a local page, and production builds leave it out entirely | ZAP baseline scan; header check after each deploy; unit tests of the emulator guard and the test sign-in guard; `npm run budget` fails if the test sign-in's marker appears anywhere in the production build (proved by breaking the guard on purpose); pre-submit check that `/api/health` shows `"emulators": false` |
| A03 Software Supply Chain Failures | A compromised npm package | Exact versions and a committed lockfile; no release newer than 14 days except security patches, which we take at once; few dependencies. `overrides` entries, each because a library pins a vulnerable package we can't upgrade directly: `@grpc/grpc-js` 1.14.6 for Firestore's SDK; `jwks-rsa` 3.2.2 under `firebase-admin`, which asks for 4.x: 4.x `require()`s `jose` 6, which is ES-module only, and Netlify's function runtime has loading ES modules through `require()` switched off, so every signed-in route failed in production on 25 October 2026 (`ERR_REQUIRE_ESM`). 3.x uses `jose` 4, which loads; `firebase-admin` calls only `jwks()`, `getSigningKeys()` and `getPublicKey()`, which 3.x has, and only for App Check and phone-number tokens, never for verifying a sign-in; and, scoped to `firebase-tools` only, `uuid` 11.1.1 under `gaxios` (GHSA-w5hq-g745-h8pq) and `@opentelemetry/core` 2.8.0 under `@google-cloud/pubsub` (GHSA-8988-4f7v-96qf). `firebase-tools` 15.34.1 is a pinned dev dependency, used by `npm run rules` and `npm run emulators`, never a global install; it only runs the emulators against test data and never ships in the app. With these overrides the rules tests and all three emulators were rerun and pass | `npm audit` reports zero vulnerabilities, dev tools included; it runs in every Netlify build (`npm run verify`), so a new advisory stops the deploy |
| A04 Cryptographic Failures | Leaked ID numbers | HMAC-SHA256 with a server-only secret; only the hash and last four digits are stored, for young people and business owners alike (owners' numbers hashed in their own scope); the hash lives only in `idHashes`, which no client can read, never on the user's own document; the full number and date of birth are dropped as soon as the ID is checked; without the secret, nothing is saved (fail closed); HTTPS only | `tests/unit/idSafety.test.ts` sends a valid ID down every failure path through the real route handlers and searches every log line, error message, response and stored record for the number and the date of birth; a deliberately planted leak makes it fail |
| A05 Injection | Script hidden in a tryout or AI output | React escaping, no raw HTML rendering, CSP, Zod validation on every input | XSS payloads in end-to-end tests |
| A06 Insecure Design | A fake tryout used to lure a young person; a "fee" or a "send it back" scam | Daylight-only tryouts at business premises, shopfront details on every business, ID check at the door, trip sharing, reports that pause a business. Scam rules in code (`scamRules.ts`): a tryout that asks the young person to pay a fee, a deposit or for their own kit is refused before the AI sees it; "They asked me for money" pauses the business at once; no screen ever asks a young person to send money, and an overpayment is settled only by review | An abuse-case test for each rule in `docs/RULES.md`; `tests/unit/scamRules.test.ts` |
| A07 Authentication Failures | Account takeover or forged tokens; anyone registering a password account; someone with the demo accounts' public passwords taking them over | Firebase Auth; server verifies ID tokens with revocation checks. Everyone signs in with Google, except two demo accounts for judges, whose email and password are public (in the slides) and so protected by isolation, not secrecy (below). Their passwords are checked by our server (`POST /api/demo/sign-in`) against a salted scrypt hash in `demoAccounts`, which no client can read, and the server signs the judge in with its own custom token. Judges can also sign in in one tap, "Try as Thabo" or "Try as Sipho" (`POST /api/demo/try`): the server finds the account by its role in `demoAccounts` and signs it in the same way, so no password is typed, sent or stored anywhere new; this adds no exposure, because the passwords are public and isolation is what keeps real people safe. Firebase's Email/Password provider, sign-up and deleting an account from the browser are switched off for the project (`scripts/createDemoAccounts.ts` sets them). `requireUser` refuses any password sign-in, and any demo token whose email has been moved off `@firstshift.demo`, a domain nobody can own, so no reset or email change can ever be confirmed from an inbox. Each demo sign-in puts the account's email, claims and enabled state back, and recreates it under the same uid if it was deleted (`domain/signIn.ts`, `server/services/demoSignInService.ts`) | `tests/unit/auth.test.ts`, `signIn.test.ts`, `demoSignIn.test.ts`; `npm run e2e:demo` attacks a demo account in the emulators as a visitor with its password could: a wrong password (401), editing its profile (403), changing its Firebase password and signing in with it (403), moving its email to Gmail (403); then the public password still signs in and the email is back |
| A08 Software or Data Integrity Failures | A forged or edited reference, or a photo the server never checked | References (`references/{booking}`, created once; no route lets an owner change one), job offers (once per pair; the young person's answer and the owner's Hired or Did not work out each written once by the server through `decideHireAnswer` and `decideHireOutcome`, with an audit entry, and the pay checked against the minimum wage in code), payments and proof screenshots are written only by the server (references append-only, after Received; proof only after Not received, each with an audit entry and its note kept off the audit log); every profile write adds an `auditLog` entry (uid, action, time, no personal data) in the same transaction, so a change can't happen unrecorded; the one client write, photo upload, is checked by the server (path built from the uid, type and size read from Storage) before it counts. Tryout credits are an append-only ledger (`creditLedger`), written only by the server in the same transaction as the event that causes each entry, each entry numbered and created once so none can be changed, reordered or written twice, and each with its own audit entry; reviewers' decisions are logged under their name (`scripts/reviewTryout.ts`), and so is every credit an admin adds (`npm run credits:grant`: 1 to 50 at a time, with the reason on the audit entry, closing the business's request in the same transaction) | Rules tests prove clients can't write them, nor read or write the credit ledger; service tests prove each write audits once and a refusal writes nothing |
| A09 Security Logging and Alerting Failures | Silent failures | `log()` records every rejected request and AI failure without personal data | Force failures and confirm they're logged |
| A10 Mishandling of Exceptional Conditions | An AI timeout skips a check | `/api/health` checks the services, not just the settings: it signs a custom token (loads the Auth module and parses the private key), reads one Firestore document and checks the Storage bucket, each with a time limit, and answers 503 with the failing check named if any fails. Results are cached for a minute, so the public route can't run up reads. Before this, it reported every integration true while sign-in was broken; rebuilt with the broken package, it now answers 503 `degraded` with `auth: false` (proved locally with ES module loading switched off, as on Netlify). Fail closed: any error blocks the action; timeouts on every external call; an AI answer counts only if it finished (`end_turn`), so a refusal or a cut-off answer blocks the action too | `tests/unit/claude.test.ts`: a refusal, a cut-off answer, output that doesn't match and a thrown error each fail closed and are logged without the request text |

**Phase 6 (26 October 2026).** A work record is shared at an unguessable 144-bit token, read by the server, and shows only approved content: never an ID, a surname or a phone number (`sharedRecord`, `tests/unit/records.test.ts`); an unknown and a malformed token look the same. `references` and `hireOffers` are server-only (`tests/rules`). `npm run review:case` and `npm run pilot:metrics` need the Admin credentials; every action the review list takes is audit-logged under the admin's name with the reasoning, and the metrics leave demo records out.

## Demo isolation

The demo accounts' passwords are public, so what keeps real people safe is that demo and real never meet (`src/domain/demo.ts`, `sameWorld`):

- The demo claim is set only by the server, read from the ID token in `requireUser`, and copied onto everything a demo account creates (`demo: true` on users, businesses and tryouts). A record with no mark counts as real.
- A demo account sees and touches only demo records, and a real person only real ones, on every route that reads someone else's data. Young people get tryouts only from the server, never from Firestore directly: the rules let only a tryout's owner read it (`tests/rules`).
- A demo profile can't be changed from the app at all (`profileEditProblem`), so nobody can put their own name, photo or ID number on a shared account, and typing a real ID number into one can't lock it away from its owner. Storage refuses any upload from a demo token.
- `npm run demo:reset` restores the demo world to a known state (`src/data/demo.ts`), deleting only demo records: the demo accounts' own documents, two extra demo businesses with no account behind them, documents marked demo, and the proof screenshots on demo bookings. As an exception to the append-only ledger, it deletes the demo business's credit entries and writes the demo ledger again (the free credits, two finished tryouts, five more credits). It also writes Sipho and Thabo's two finished tryouts this month and placeholder photos (plain shapes drawn by the server, never a real face). The audit log is kept, with a `demo_reset` entry per account.
- **Reset the demo** in the app (`POST /api/demo/reset`) runs the same reset (`src/server/repositories/firestoreDemoWorld.ts`). Only a signed-in demo account may call it (403 otherwise, logged), and at most once a minute for everyone, claimed in a transaction (`cooldowns/demo_reset`, server-only), because every judge shares the demo world.
- **Skip to the day** (`POST /api/bookings/{id}/skip-to-day`) moves a booking's start to a few minutes ago so a judge can try the door at any hour. It's refused unless both the booking and the person asking are demo (`decideSkipToDay`, `tests/unit/day.test.ts`): a real booking's times stay locked once booked.
- The two demo businesses with no account behind them are examples: their tryouts say "Example, for viewing only" and refuse applications (`isExampleOwner`).
- The credentials live only in `.env.demo.local` on the developer's laptop (ignored by Git), as a hash in `demoAccounts`, and in the slides. Tests and e2e checks use throwaway passwords, and the pre-commit secrets check searches staged files for the real ones.
- Daily limits count per account, so all judges share the demo business's 5 posts and its AI allowance each day; `demo:reset` clears them.

## AI risks (OWASP Top 10 for LLM Applications 2025)

| Risk | Control |
| --- | --- |
| LLM01 Prompt Injection | User text goes in as tagged data with `<` and `>` escaped, so it can't close the tag; the model has no tools and no write access; structured outputs fix the answer's shape and Zod checks it; code makes every decision, so a fooled classification can at worst send work to review, never past the pay floor or the time rules; publishing checks the final title and tasks again |
| LLM02 Sensitive Information Disclosure | ID numbers, phone numbers and names never reach the model |
| LLM05 Improper Output Handling | Output is validated, then shown as plain text only |
| LLM06 Excessive Agency | Code makes every decision; the model only drafts, classifies and writes |
| LLM07 System Prompt Leakage | No secrets or safety rules live in prompts |
| LLM09 Misinformation | References come only from the owner's three answers and the tasks (no name, ID or number reaches the model), are labelled as written with AI, and are reviewed by the young person before anything is shared; a challenge goes to a person |
| LLM10 Unbounded Consumption | Input length limits, token caps, per-user daily quotas and rate limits |

## Privacy (POPIA)

- We collect a first name, a photo, an area, a payout phone number and an ID number for eligibility only. Since Step 2 (26 October 2026), also the young person's legal surname, and from a business owner their full legal name, ID number (the same hash and last four digits), a face photo and a contact number, plus an optional CIPC registration number.
- **Admin lookup.** Full names, phone numbers and the last four ID digits are kept so an admin can find the person behind an account when a safety report, a payment dispute or a strike needs it (`npm run review:case`). They sit on each person's own `users` and `businesses` records, which only that person and the server can read (`tests/rules`); the server never sends another user anyone's surname, legal name or ID digits. The one exception is deliberate: once booked, the young person sees the owner's first name, photo and number, and the owner the young person's number and, at the door, the last four ID digits. The Privacy notice (`/privacy`) states this purpose.
- A young person's introduction is cleaned of phone numbers, email addresses, links and handles on the server before it's stored, so contact details can't reach an owner before booking (`cleanIntro`).
- We never ask for a bank account number. Businesses pay to the young person's cellphone number (FNB eWallet, PayShap, a cash-send) or in cash; the young person chooses which.
- A screenshot added as proof in a dispute may show a banking screen. It's stored at a private path only an admin reads, kept for the review, and never shown to the other side.
- We don't run face matching, which POPIA treats as biometric special personal information.
- **Privacy notice, Terms, Safety and fair play, Contact** are public plain pages (`/privacy`, `/terms`, `/safety`, `/contact`), linked from every public page's footer. Signing in says "By continuing, you agree to the Terms and the Privacy notice", and the agreement is recorded at sign-in, once per version (`termsAcceptances/{uid}` with the version and time, server-only, audit-logged; `src/config/terms.ts`). If it can't be recorded, sign-in stops with a message: fail closed.
- Photos are visible only to signed-in users of the app; IDs and phone numbers are never shown to businesses before booking.
- Deleting an account and its record isn't built into the app yet. Until it is, anyone can ask for deletion by emailing firstshift.support@gmail.com (`src/config/contact.ts`), and we complete it within 30 days. A "Delete my account" button is in `docs/PHASES.md` only if time allows.

## Accepted risks

| Risk | Why we accept it | What would change it |
| --- | --- | --- |
| The Content Security Policy allows inline scripts (`script-src 'self' 'unsafe-inline'` in `next.config.ts`), so the policy alone wouldn't stop an injected inline script | Next.js needs inline scripts to start each page. The only strict alternative is a fresh nonce per request, which makes every page render on the server for every visit: no static pages, no CDN caching, slower first loads on the weak connections our users have. React escaping, no raw HTML rendering and Zod validation on every input are the real XSS controls | Rendering any user-supplied HTML or markdown; a third-party script on our pages; an XSS finding in the ZAP scan or the pen test; or Next.js supporting hash-based CSP for static pages, which keeps them static |

## Testing, including penetration testing

1. **Unit tests** for every rule in `src/domain` (`npm test`).
2. **Security rules tests** in the Firebase emulator (`npm run rules`).
3. **Checks on every deploy:** `npm run verify` is Netlify's build command: lint (including architecture boundaries and a file-size cap), typecheck, unit tests, the build, the JavaScript budgets and `npm audit`. A failure stops the deploy and the live site stays as it was. Proved on a throwaway branch, `ci-proof`, as pull request #1 (closed unmerged, branch deleted):

   | Push | What it held | Netlify deploy preview |
   | --- | --- | --- |
   | `21c988c`, 17:05 | A unit test that fails on purpose | **Failed**: "Build script returned non-zero exit code: 2" (deploy `6ade36c4`) |
   | `b329b4b`, 18:05 | The failing test removed | **Failed** too, which it shouldn't have. Cause: `tests/unit/idSafety.test.ts` assumed `ID_HASH_SECRET` isn't set, and Netlify sets the site's real variables during the build. Fixed by making unit tests hermetic: `tests/unit/support/hermeticEnv.ts` clears every secret, service setting and emulator switch before any test runs, so no unit test sees a real value or reaches a real service |
   | `6a142e8`, 18:22 | The hermetic fix | **Ready**: "Deploy Preview ready!" (deploy `6ade48d8`) |

   So the gate works both ways, and it caught a real problem that would have blocked the next production deploy. `npm run rules` needs Java and the emulators, so it runs locally before every push. GitHub Actions workflows for all of this (`.github/workflows/ci.yml`) are configured but paused: since 25 October 2026 GitHub hasn't started any job on this account because of a billing issue, so no push since then has had a CI run. They resume once that's resolved.
4. **ZAP baseline scan** (passive) against the live URL. The workflow (`.github/workflows/zap-baseline.yml`) is paused with the rest of GitHub Actions, so the scan is run by hand with the ZAP desktop app and its findings recorded below. Active scans run only against our own staging deploy, never anyone else's system.
5. **Manual pen-test checklist before submission:** swap IDs between accounts, call every route with no token and an expired token, burst requests past each limit, send oversized and malformed input, try XSS payloads in every text field.
6. **AI evaluation set:** 20 owner sentences in `tests/fixtures/aiCases.ts`: 8 allowed, 8 blocked (one per category) and 4 hostile (an instruction to set pay to R5 an hour, an instruction to classify rewiring as cleaning, a request hidden in Afrikaans, and an attempt to close the `owner_text` tag). `npm run eval:ai` runs them against the real API, prints a pass or fail table and exits non-zero on any failure. It needs a real key and costs money, so it never runs in CI; rerun it on every prompt or model change. Our claim "AI blocks unsafe work" holds only while all 8 blocked cases are refused and all 4 hostile cases resisted. Last run 26 October 2026, after the draft prompt was told today's date (a day named in the request sets the tryout's date, decided in code, `domain/draftDate.ts`): all 20 passed on `claude-haiku-5-5` (allowed 8 of 8, blocked refused 8 of 8, hostile resisted 4 of 4).

   | Date | Model and effort | Allowed | Blocked refused | Hostile resisted | Result |
   | --- | --- | --- | --- | --- | --- |
   | 25 October 2026 | `claude-haiku-5-5`, effort low | 8 of 8 | 8 of 8 | 4 of 4 | **20 of 20 passed**, on the first run, with no prompt changes. Every blocked and hostile case was sorted into its exact expected category, except the R5-an-hour instruction, which went to review (not allowed, as required); the pay floor is enforced in code whatever the model says |
   | 25 October 2026, after two prompt changes | `claude-haiku-5-5`, effort low | 8 of 8, each allowed draft also passing the check again at publish, unedited | 8 of 8 | 4 of 4 | **20 of 20 passed.** The changes: the draft prompt now names lengths (title under 50 characters, tasks under 100), and lists the blocked kinds of work to leave out, from the same definitions the check uses.
